- Ataques reais à API REST (PostgREST 12 + JWT de aluno e de anônimo), com dados semeados e apagados depois: ler material pago, ler curso/aula em rascunho, escrever em `user_roles`, `enrollments`, `orders` e `profiles.id`, chamar `fulfill_order`, `admin_record_manual_sale` e `admin_students`, gravar progresso sem matrícula e ler `payment_events`. **Todos foram negados** (42501, ou só os dados permitidos).
- `npm run build` seguido de `grep` em `.next/static`, procurando nomes de segredo, prefixos de chave (`sb_secret_`, `abc_prod_`, `abc_dev_`), `service_role` e a chave HMAC: só aparece o literal `sb_secret_` dentro do supabase-js (checagem de prefixo da biblioteca). Nenhum segredo apareceu.

## Verificado (sem achado)

1. **Server Actions:** todas usam `userAction`/`adminAction` (o guard roda antes de ler o input e de qualquer I/O) com zod, ou são ações de visitante com zod e `sanitizeNextPath` (`signIn`/`signUp`/`requestPasswordReset`/`resetPassword`). `signOut` é POST e exige sessão. `user_id` sempre vem da sessão. O preço vem do banco (`course_catalog`), e o `orders.amount_cents` fica imutável pelo trigger. A busca de pedidos (`.or()`) remove `,()*%_\"` antes de montar o filtro e só um admin a usa. Não há `'use server'` fora de `actions.ts`.
2. **RLS e grants:** RLS ativa nas 11 tabelas. `user_roles`, `orders` e `payment_events` são somente leitura para `authenticated`. Em `enrollments`, só o admin insere (`admin_grant`, assinando como ele mesmo), e `purchase` exige pedido `paid` (`enrollments_guard`). `profiles` aceita UPDATE só em colunas pessoais, com CHECK de formato (`avatar_url` só `https://`). Curso `draft` só é visível ao admin. `archived` só para quem tem acesso. As views são `security_invoker`. Toda função `security definer` tem `search_path=''` e `revoke` de `public`. `fulfill_order`/`refund_order` só podem ser chamadas por `service_role`. As funções de admin checam `is_admin()` (42501).
3. **Webhook:** o segredo é comparado com `timingSafeEqual`, depois vêm HMAC sobre o corpo bruto, limite de 64 KB, dedupe por `provider_event_id` e reconsulta obrigatória (`PAID`/`REFUNDED`). O id da cobrança gravada no pedido tem precedência sobre o do evento. Cobrança já usada por outro pedido é recusada. `fulfill_order` é idempotente e compara valor e cobrança dentro da transação. Eventos `devMode` são ignorados em produção. O payload é guardado sem dados do pagador.
4. **Storage:** `course-content` é privado e não tem SELECT para aluno. O download é signed URL de 600 s gerada depois de ler o material com o client do usuário (RLS). Upload, update e delete só para admin. O path é checado no servidor (`isPathInLesson`) e no banco (`lesson_materials_storage_path_safe`). Os buckets não aceitam HTML, SVG nem JS.
5. **Redirects:** `sanitizeNextPath` rejeita `//`, `\`, esquemas, controle/espaços (também com codificação dupla) e normalizações como `/.//evil` (a checagem é refeita depois do parse). `/auth/callback` e `?code=` na raiz só encaminham para paths internos. **Cache:** `private, no-store` em `/aprender`, `/inicio`, `/minha-biblioteca`, `/conta`, `/checkout`, `/admin`, no callback e no webhook. **CSRF de actions:** a checagem de Origin do Next continua ativa (não há `allowedOrigins`). **`/dev/*`:** `notFound()` em produção no layout e nas páginas.
6. **Segredos:** `SUPABASE_SECRET_KEY` e as chaves da AbacatePay só aparecem em módulos com `import 'server-only'` (`lib/env/server`, `lib/supabase/service`, `payments-webhook/store`, `orders/service`, `materials/storage`, `checkout/actions`). As únicas `NEXT_PUBLIC_*` são URL, publishable key e site URL. O bundle client está limpo.
7. **Conteúdo do admin para o aluno:** o markdown é convertido por parser próprio em elementos React (sem `dangerouslySetInnerHTML`). Links passam por `safeExternalUrl` (só http(s), sem credenciais) e o banco também restringe `external_url` a http(s). Embeds: `video_id` restrito a `[A-Za-z0-9_-]` no banco e no `buildVideoEmbed`, com host fixo (`youtube-nocookie.com`, `player.vimeo.com`).
