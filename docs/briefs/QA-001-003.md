3. **Mock da AbacatePay**: servidor HTTP local mínimo (`e2e/mocks/abacatepay.ts`) implementando `POST /transparents/create`, `GET /transparents/check`, `POST /transparents/refund`, `POST /transparents/simulate-payment`. O teste de compra dispara o webhook real do app (`/api/webhooks/abacatepay?webhookSecret=…`) com o payload do evento `transparent.completed` (formato em `docs/payments.md` §4/§5) e também cobre o plano B (polling reconsulta → `PAID`).
4. **Fluxos (QA-003)** — cada um com dados próprios (emails únicos), sem depender de ordem:
   - Visitante: landing → catálogo → página do curso → "Comprar" leva a `/entrar`.
   - Cadastro → confirmação de email via Inbucket/Mailpit do Supabase local (API HTTP; porta no `config.toml`) → `/inicio`.
   - Admin (criado via SQL/service role no setup): cria curso, módulo, aula com material de texto, envia capa, publica; aparece no catálogo.
   - Aluno compra (PIX mock) → página do pedido vira "Pagamento confirmado" → curso em Minha biblioteca → abre aula → marca concluída → progresso aparece.
   - Admin atribui curso a outro aluno → aluno acessa; admin revoga → acesso negado.
   - `/conta`: salva nome; `/conta/pedidos` lista o pedido; 404 de marca em rota inexistente.
   - Segurança básica: aluno em `/admin` é bloqueado; aula paga sem acesso não mostra material.
   - Em todos os projects: sem overflow horizontal nas telas visitadas (`scrollWidth - innerWidth === 0`).
5. **CI**: job `e2e` (depois de `ci`) que sobe Supabase (`npx supabase start`), aplica migrations, cria `.env` a partir de `npx supabase status -o env`, sobe o mock, `npm run build && npm start`, roda `npm run test:e2e`, publica `playwright-report` como artifact em falha.
