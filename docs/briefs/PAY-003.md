# PAY-003 — Webhook AbacatePay e concessão de acesso

**Agente:** A07 Payments · **Modelo:** Opus 5.5 · **Esforço:** alto

## Objetivo
Receber os eventos do AbacatePay com segurança e liberar/revogar acesso **somente** via `fulfill_order` / `refund_order`, de forma idempotente.

## Leia (somente isto)
- `CLAUDE.md`
- `docs/payments.md` → §4 (verificação, pseudocódigo), §5 (eventos → status), §8 (reembolso), "Pendências"
- `docs/database.md` §4 → `fulfill_order`, `refund_order` (códigos de resultado) e tabela `payment_events` (grep)
- `supabase/migrations/20261008000003_rls_functions.sql` → só `fulfill_order` e `refund_order` (grep)
- `src/lib/payments/abacatepay.ts` (`getPixStatus`) e `src/lib/env/server.ts` (`getPaymentsEnv`), `src/lib/supabase/service.ts`

## Entregas
1. **Migration `supabase/migrations/20261009000007_fulfill_failed_orders.sql`**: `create or replace` de `fulfill_order` aceitando também `failed` → `paid` (caso: timeout no PAY-002 marcou o pedido `failed`, mas a cobrança existia e foi paga; o provedor confirmou). Manter `canceled` recusado. Mantenha assinatura, grants e o resto idêntico. Atualize `supabase/tests/06_commerce_functions.test.sql` (caso failed→paid) e `docs/database.md` §4.
2. **`src/app/api/webhooks/abacatepay/route.ts`** (Node runtime, `POST`; `GET` → 405):
   - `webhookSecret` da query comparado com `timingSafeEqual` (comprimentos iguais) → 401; nunca logar a URL/segredo.
   - corpo bruto (`request.text()`), limite de tamanho (ex. 64 KB → 413); `X-Webhook-Signature` = HMAC-SHA256 base64 com a chave pública da AbacatePay (constante em `src/lib/payments/abacatepay-webhook.ts`, com link da doc) → 401 se inválida.
   - parse mínimo (zod só dos campos usados): `id` do evento, `event`, `devMode`, `data` (id da cobrança, `externalId`, `amount`, status).
   - em produção (`ABACATEPAY_API_KEY` `abc_prod_`), recusar eventos `devMode: true` (200 + ignorado, para não re-tentar).
   - `insert` em `payment_events` (`provider_event_id` único) com service client; conflito → 200 "duplicado".
   - resolver o pedido por `externalId` (= `orders.id`) e conferir `provider_billing_id` quando houver.
   - `transparent.completed`: **reconsultar `getPixStatus`** (obrigatório — a assinatura não prova origem) e só se `PAID` chamar `fulfill_order(order.id, billing_id, amount do provedor, event_id)`.
   - `transparent.refunded` e `transparent.lost`: reconsultar status quando a API permitir; chamar `refund_order`.
   - `transparent.disputed`: só registrar (`payment_events`) e log de alerta.
   - Respostas: 200 para processado/duplicado/erro de dados (`amount_mismatch`, `invalid_status`, `billing_mismatch`, `order_not_found` — gravados em `processing_error`); 5xx só para falha transitória (banco/provedor indisponível) para o provedor re-tentar.
   - Logs estruturados sem PII.
3. **`src/features/payments-webhook/handler.ts`** (lógica pura testável, a rota só adapta Request/Response) + testes.
4. `docs/payments.md`: seção "Implementado" curta com a URL a configurar no painel e o comportamento.

## Critérios de aceite
- Testes (Supabase e fetch mockados): segredo errado → 401; assinatura inválida → 401; corpo grande → 413; evento duplicado → 200 sem efeito; `completed` com reconsulta ≠ PAID → não chama `fulfill_order`; `amount_mismatch` → 200 + `processing_error`; banco indisponível → 500; `refunded` → `refund_order`; `disputed` → só registra; `devMode` em prod → ignorado; nada de acesso concedido fora de `fulfill_order`.
- Migration aplica no PG16 local e a suíte pgTAP passa (cluster `/run/pgsmoke`, pgTAP no schema `tap`: `PGOPTIONS="-c search_path=public,tap" pg_prove`).
- `lint`, `typecheck`, `test`, `build` passam sem env. O proxy já exclui `/api/webhooks` (confirme em `src/proxy.ts`, não edite).
